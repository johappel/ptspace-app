# Analyse und Entscheidungen – 2026-08-22

## Ausgangslage

Reale Harness-Tests mit opencode waren wiederholt nicht erfolgreich. Die Untersuchung
(`docs/analysis-2026-07-21.md`) zeigte: Die Backend-Domäne (130+ Tests) ist stabil,
die Fehler lagen im Transportlayer der opencode-Runtime:

- Provider-/Modell-Trap der CLI (`opencode/*`-Modelle erzwingen Provider ohne Key-Mount),
- JSONL-Antwortparsing,
- Docker-Image, `auth.json`-Secret-Mounts,
- Windows-Spawn-Probleme mit `.ps1`-Wrappern (`shell:false`, ENOENT),
- Healthcheck meldete `ready` ohne echten Modellaufruf.

## Entscheidung: DirectLlmAdapter als Standardpfad

Die App nutzt keinen freien Agenten-Loop im Produkt; Worker sind vertragsgebunden.
Die Agenten-Infrastruktur von opencode kauft daher Komplexität ohne Produktwert im
Standardpfad. Neu:

1. **Refactor:** harness-unabhängige Logik aus `OpenCodeDockerAdapter.ts` in gemeinsame
   Module ausgelagert (~400 Zeilen): `prompts.ts`, `workspaceDiff.ts`, `replyTranslation.ts`.
2. **Neuer Adapter** `DirectLlmAdapter` (`backend/src/services/harness/DirectLlmAdapter.ts`):
   OpenAI-kompatible Chat-Completion über HTTP, injizierbarer Client, kein Docker/CLI/JSONL.
   Dateioperationen führt das Backend selbst aus → Permission-Policy trivial erfüllbar.
3. **Konfiguration:** `PTSPACE_HARNESS=direct-llm`, `PTSPACE_DIRECT_LLM_BASE_URL/MODEL/TIMEOUT_MS`,
   Key generisch über `PTSPACE_LLM_API_KEY` (Fallback `OPENROUTER_API_KEY`).
4. opencode bleibt als optionale Agenten-Stufe erhalten (Kernel-Evolution), nicht mehr Default.
